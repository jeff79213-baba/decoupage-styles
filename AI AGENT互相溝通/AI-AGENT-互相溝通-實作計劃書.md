# AI Agent 互相溝通 — 多引擎交叉審查工作流 實作計劃書

> **文件版本：** v1.0（2026-08-28）
> **狀態：** 待審查（由不同 AI 引擎／模型審查後回饋，審查意見會寫回本文件）
> **審查要求：** 閱讀者請以「否定角度」審查：目標是否清楚、架構是否可行、
> 決策是否合理、風險是否被低估。逐項回覆下方「審查點」。

---

## 1. 專案目標（Goal）

建立一套**多引擎 AI Agent 交叉審查工作流**，讓使用者在**單一介面**下達需求後：

1. **Agent A（實作者）** 負責實作功能／修改程式碼
2. **Agent B（檢驗者，使用不同 AI 引擎）** 以對抗式角度檢驗 A 的產出是否達成需求
3. **不合格 → 回饋給 A 修正 → B 再檢驗**，反覆循環
4. 直到 **B 判定達標** 才輸出最終報告或程式碼

**核心原則：** 實作者與檢驗者必須使用**不同的模型／引擎**，
避免「同一個模型自我認證」的盲點。

---

## 2. 應用情境（Context）

使用者實際想解決的問題：

- 本人下達指令後，不希望只有「一個 AI 一次做完就交差」
- 希望有**另一個獨立引擎**負責挑毛病，形成生產線品質關卡
- 反覆循環直到「檢驗者認可」才算完成，而非「實作者自我感覺良好」
- 使用者的專案資料夾名即為「AI AGENT互相溝通」— 本專案即為此概念的落地實作

### 本專案的「狗糧測試」情境（Dogfooding）
使用者已明確表達：**這份計劃書本身**就要先送給另一個 AI 審查，
用來驗證整套工作流真的可行。因此本專案第一個實際案例即為
「計劃書 → 外部審查 → 依意見修正 → 再審查」的循環。

## 3. 架構設計（Architecture）

### 3.1 整體流程

```
┌─────────────┐
│  使用者下達指令  │     需求文件（.md / 天然語言）
└──────┬──────┘
       │
       ▼
┌─────────────┐      ┌──────────────────┐
│  Orchestrator  │────▶│  需求規格化（明確驗收標準）  │
│  (主控協調者)   │      └──────────────────┘
└──────┬──────┘
       │
       ▼
┌─────────────┐  工作分支/隔離工作目錄   ┌─────────────┐
│  Agent A     │═════════════════════════▶│  Agent B     │
│  實作者/實作方  │◀════════════════════════++│  檢驗者/驗收方  │
└─────────────┘   檢驗回饋(不合格項目)    └─────────────┘
       ▲                                          │
       │                                          │ 判定
       │                ┌─────────────┐           │
       └────────────────│ 未達標：回到 A │◀──────────┘
                        └─────────────┘
                        ┌─────────────┐
       ┌────────────────│ 已達標       │
       │                └─────────────┘
       ▼
┌─────────────┐
│ 輸出最終報告/程式碼  │
└─────────────┘
```

### 3.2 引擎組合（引擎可插拔，至少含兩種不同引擎）

| 角色 | 建議工具 | 備註 |
|------|---------|------|
| Agent A（實作） | Claude Code / OpenCode + Claude | 主力實作者 |
| Agent B（檢驗） | Codex CLI（GPT）/ Gemini CLI / 另一 Claude 實例 | **必須與 A 不同引擎或至少不同模型族** |
| Orchestrator | Node.js 腳本 / Claude Code plugin | 主控、管循環 |

### 3.3 技術選型（Technology Stack）

- **環境：** Windows PowerShell（使用者為 win32）
- **主要實作語言：** Node.js（已有 CLI 生態最成熟）
- **呼叫工具：** 各引擎的 CLI headless 模式
  - Claude Code：`claude -p "<prompt>"`
  - Codex：`codex exec "<prompt>"`
  - Gemini：`gemini -p "<prompt>"`（依官方 CLI）
- **檔案溝通媒介（File-based handoff）：** 各步驟產出以檔案交換
  （需求 md、檢驗意見 md、修正紀錄），不依賴對話記憶

## 4. 決策紀錄（已定案決策）

| 編號 | 決策 | 理由 |
|------|------|------|
| D1 | 採用「檔案為溝通的唯一事實來源」 | 各引擎無共享對話記憶，檔案可審計、可重跑、可給人檢查 |
| D2 | Agent B 預設為「對抗式」：主動找失敗理由而非背書 | 避免「實作方問檢驗方要過嗎」的自我認證 |
| D3 | 循環上限（預設 5 輪），達上限仍未過 → 轉人工 | 避免無限迴圈燒 token |
| D4 | 每個引擎 call 之間刻意輪換或冷卻，避免快取效應共享判斷 | 提高不同引擎獨立性 |
| D5 | 未達標的修正指令：**只帶回 B 的具體意見**，不帶 A 的原始思考 | 讓 A 無法靠著「自己解釋」辯護，只能照意見修 |

## 7. 實作任務分解（Task Breakdown）

> 此為初步規劃。審查後若決策點變更，會重寫此區。

### Task 1：引擎封裝模組
建立 `claude.mjs`、`codex.mjs`、`gemini.mjs`，各自提供
`run(prompt, cwd)` 介面，返回 stdout + exit code + 耗時。
共用 `lib/exec.mjs` 處理子行程叫用與錯誤（工具不存在、逾時、配額）。

### Task 2：提示詞模板
`implementer.txt`：指示 A「只做需求文件所列，改動最小，輸出做了哪些事」。
`reviewer.txt`：指示 B「以對抗角度，對照需求與驗收標準逐項檢驗，
輸出 JSON 判定：`{verdict: PASS|FAIL, findings: [...], reasons: [...]}`」。

### Task 3：主迴圈 `run-review.mjs`
流程（每輪）：
1. 讀需求文件 → 呼 A（實作）→ 產出工作目錄內變更
2. 呼 B（檢驗）→ 解析 verdict
3. PASS → 寫 `結果-<任務名>.md`，結束
4. FAIL → 若輪數 < MAX_ROUNDS：把 B 的 findings 包成「修正指令」給 A，回到 2
5. FAIL 且達上限 → 標記人工介入，輸出累積檢驗意見

### Task 4：需求規格化
建立「需求文件模板」：含目標、範圍、驗收標準表格、成功條件。
Orchestrator 產生需求文件後才開始循環。

### Task 5：測試與驗證
- 單元測試：verdict 解析、循環輪數上限、findings 打包
- 引擎封裝以空跑（fake CLI 回傳固定輸出）測試
- E2E：真正的「雙引擎簡短需求」跑一輪（費用壓到最低）

## 8. 風險與緩解（Risk & Mitigation）

| 風險 | 影響 | 緩解 |
|------|------|------|
| 引擎 CLI 未安裝或未登入 | 無法呼叫 | Task 1 預檢（preflight），缺工具即報錯誤清單 |
| token 費用無上限 | 成本爆表 | 強制 MAX_ROUNDS、每輪記成本、輸出摘要 |
| 不同引擎理解偏差 | A 修了 B 不認同 | 需求內含結構化驗收標準，B 對照逐項檢驗 |
| 無限修正迴圈 | 停不下來 | MAX_ROUNDS + 達上限轉人工（D3） |
| A 嘗試辯護而非修正 | 浪費循環 | D5：只給 B 的意見，不給 A 自我解釋空間 |
| 兩引擎其實是同一模型墊背 | 交叉意義失效 | preflight 檢查引擎 ID 確實不同（D4） |

## 9. 驗收標準（本計劃書的驗收標準）

本專案本身算「成功」的定義：

- [ ] 使用者在單一介面（CLI）下一個需求文字，即可自動跑完整個循環
- [ ] 實作者與檢驗者實際使用兩種不同引擎（可驗證不同 CLI 被呼叫）
- [ ] 不合格時檢驗意見會被自動回饋，實作者自動修正，且修正有軌跡可查
- [ ] 達標後自動產生最終報告
- [ ] 達循環上限自動停，不無限燒成本
- [ ] 本計劃書經「另一 AI 審查 + 依意見修正」的流程走過一遍，過程產出被保留證明可行性

## 10. 審查事項（FOR REVIEWER）

請另一位 AI（閱讀此文件者）回覆以下項目：

1. **目標模糊嗎？** 第 1、2 節是否清楚描述要做什麼？
2. **架構上有沒有根本缺陷？** 第 3 節的流程是否可行？哪一步你認為會卡住？
3. **決策點 Q1–Q7** 各給予「同意／反對／改進」及一句理由。
   - 特別是 Q2：自建 vs 現成工具（tagteam / review-loop），你推薦哪個？
4. **風險清單（第 8 節）** 有沒有重大遺漏？
5. **任務分解（第 7 節）** 有沒有缺漏的環節？
6. **你認為最可能失敗的一點是什麼？** 為什麼？

審查意見格式建議：

```
### 審查意見
- 審查者引擎：<填寫>
- 審查日期：<填寫>

Q1：<同意/反對/改進> — <理由>
...
6. 最可能失敗點：<答案>
```

審查完請將意見寫入同資料夾新檔：`審查意見-<引擎名>-<日期>.md`
或直接回覆於本文件下方。實作者（另一 AI）將依意見修正計劃書並回覆承辦項目。
